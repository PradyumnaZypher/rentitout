# Phase 11: Razorpay Route Onboarding & Platform Fee Foundation

## 1. Route Onboarding Architecture
Phase 11 implements the technical foundation for onboarding listing owners onto Razorpay Route. When an owner navigates to `/dashboard/payouts`, they can securely initiate the onboarding process. The process uses the `create-route-account` Edge Function to securely abstract the Razorpay Route Accounts API and returns a `provider_account_id` back to the owner's `payout_profiles` record.

## 2. Provider Account Mapping
- Database mapping: `auth.users` -> `payout_profiles.provider_account_id`.
- The provider ID is never generated by the frontend. The Edge Function securely provisions the linked account (using Razorpay's `/v2/accounts` API) or identifies an existing account, mapping it 1:1 with the owner's Supabase User ID.

## 3. Internal Status Model
The `payout_profiles.kyc_status` now tracks exact onboarding lifecycle states:
- `NOT_STARTED`
- `CREATED` / `PENDING`
- `UNDER_REVIEW`
- `NEEDS_CLARIFICATION`
- `ACTIVE`
- `REJECTED` / `FAILED`

## 4. Webhook Flow
The `razorpay-route-webhook` Edge Function is responsible for handling server-to-server updates. It:
1. Validates the `x-razorpay-signature`.
2. Matches the event to internal status models (e.g. `product.route.under_review` -> `UNDER_REVIEW`).
3. Uses a secure Service Role RPC (`update_payout_profile_status`) to strictly update the database, preventing any unauthorized tampering from the client.
4. Generates an internal `SYSTEM` notification for the owner.

## 5. Commission Calculation
A new `platform_settings` table acts as the source of truth for platform commission (`platform_fee_bps`). The fee is currently set to `500` basis points (5%). A PostgreSQL helper `calculate_commission(amount numeric)` reliably executes pure integer arithmetic (`ROUND(amount * bps / 10000.0)`) on the gross amount, preventing any floating-point inaccuracies.

## 6. Ledger Interaction
The `financial_ledger` has been expanded to support immutable `COMMISSION_CALCULATED` events. During the `COMPLETED` booking transition trigger (`handle_booking_completion_financials`), the database now atomic writes the `OWNER_ENTITLEMENT_CREATED` record *and* a `COMMISSION_CALCULATED` record, permanently tracking the platform fee for that booking.

## 7. Security Model
- **No raw KYC storage:** Rentitout only stores the `provider_account_id` and the `kyc_status`.
- **Authoritative Data:** The frontend only queries `payout_profiles`; it never writes. Status is exclusively mutated by the secure Edge Functions.
- **Idempotency:** Re-triggering webhooks or onboarding initialization does not corrupt existing data or double-charge.
- **RPC Search Path:** All new Postgres functions use `SECURITY DEFINER` and `SET search_path = public` to prevent malicious injection.

## 8. Sandbox vs Production Boundary
This implementation successfully constructs the entire architectural flow in **Razorpay Sandbox Mode**. The UI natively supports redirecting to Razorpay's Hosted Onboarding, listening for webhooks, and tracking ledger splits. **However, live money movement and Production Route Activation remain blocked by Razorpay's business compliance requirements (e.g. ₹40 Lakhs turnover proof).**

## 9. Explicitly Deferred Functionality
The following features are *deliberately excluded* from Phase 11 and deferred to future phases:
- Real Owner Transfers (executing the Transfer from Payment API).
- Settlement Releases (`on_hold` mutation).
- Live Production Executions.
- Transfer Reconciliations.
- Live Refund API interactions.
